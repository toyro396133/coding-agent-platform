מועמד 1 · רוטר כפול עם שפות דוגמנות שונות

קבצים

  • lib/ai/router.ts — ~460 שורות, heuristic
  • lib/ai/smart-router.ts — ~110 שורות, LLM-based
  • lib/ai/models.ts — client factory
  • lib/ai/model-definitions.ts, cost-estimator.ts, rate-limits/types.ts

הבעיה

שני מודולים קוראים לאותו שם — routePrompt — אבל עם חתימות, שפות מודלים ומנועי החלטה שונים לגמרי. router.ts (synchrone, keyword-heuristics, מודלים חדשים כמו claude-sonnet-4-5) לעומת smart-router.ts (async, LLM complexity, מודלים ישנים כמו claude-3-5-sonnet-20241022). כל קורא בוחר בגורל: tasks/route.ts משתמש ב-smart-router, loop.ts, pipeline.ts ו-auto-deploy.ts ב-router.ts. הבנה של "איך בוחרים מודל" דורשת קפיצה בין 5 מודולים שכל אחד מגדיר את קטלוג המודלים מחדש.

הפתרון

למזג למודול רוטר אחד עמוק: ממשק אחד (route(prompt, opts) → {model, complexity, systemPrompt}), עם מאחורי התפר שתי אסטרטגיות (heuristic מהיר + LLM מדויק) שנבחרות פנימית. קטלוג המודלים (שמות, ספק, מחיר, tier) נאסף למודול יחיד שממנו cost-estimator ו-rate-limits צורכים.

יתרונות

  • Locality: החלטת routing = מקום אחד; סתירת השם routePrompt נעלמת.
  • Leverage: שינוי בקטלוג המודלים משפיע פעם אחת (cost, rate, rotation).
  • Testability: בדיקות fixture על קטגוריזציה בלי לרקוד סביב שני ממשקים.

מועמד 2 · אדפטר הסוכנים משוכפל ב-worker-manager

קבצים

  • lib/sandbox/agents/index.ts — executeAgentInSandbox (1 אדפטר)
  • lib/ai/orchestrator/worker/worker-manager.ts — runClaudeWorker, runCodexWorker… (2 אדפטר)
  • lib/sandbox/agents/claude.ts, codex.ts, cursor.ts, gemini.ts

הבעיה

הכלל: "one adapter = hypothetical seam, two = real". כאן יש שני מימושים מקבילים של "להריץ סוכן CLI בארגז חול": executeAgentInSandbox (עם env-override, MCP, התקנת CLI) — ובתוך worker-manager פונקציות run*Worker שמשכפלות את אותו ידע (env vars, base URLs, config.toml ל-codex) בקוד משלהן. השינויים חייבים להיעשות פעמיים, וכל סטייה (למשל טיפול שונה במפתחות) היא באג נסתר.

הפתרון

להעמיק את מודול סוכני הארגז: worker-manager הופך לאורכיסטרטור רזה שקורא ל-executeAgentInSandbox עם spec של עובד (model, instructions, apiKeys). כל הלוגיקה הספציפית-לסוכן (התקנה, env, config) חיה במקום אחד.

יתרונות

  • Deletion test עובר: מחיקת העותק ב-worker-manager מרכזת מורכבות באדפטר, לא מזיזה אותה.
  • Locality: "איך מריצים claude בארגז" = תשובה אחת.
  • Testability: האדפטר היחיד הופך למשטח בדיקה אמיתי (mock ל-Sandbox).

מועמד 3 · runOrchestrator — מונולית של 400 שורות

קבצים

  • lib/ai/orchestrator/loop.ts — runOrchestrator, composeAgentTeam
  • lib/ai/orchestrator/state.ts, modes.ts, tools.ts

הבעיה

runOrchestrator צובר חמש אחריויות נפרדות: הרכבת system prompt (mode + autonomy + rules + repo-map + queue awareness), הרכבת צוות, הגדרת כלי deployWorkerTeam מוטבע, לולאת ה-steps עם polling ל-DB, ו-checkpointing. ה-inline tool הגדול מקשה על בדיקות יחידה — הלוגיקה הקריטית (מיזוג patches, ניהול קונפליקטים) אינה נגישה דרך ממשק צר.

הפתרון

לפצל ל-3 תפרים: PromptAssembler (בונה system prompt מ-6 מקורות), ToolAssembler (מרכיב packs לפי level/autonomy), ו-LoopRunner (לולאת steps + בדיקת ביטול + checkpoint). כל אחד עמוק בפני עצמו וניתן לבדיקה.

יתרונות

  • Locality: שינוי בהנחיות autonomy נוגע רק ב-PromptAssembler.
  • Testability: הרכבת prompt ניתנת ל-snapshot test בלי מודל חי.
  • מוריד את חסם הכניסה ל-1000+ השורות הכי חמות בקוד.

מועמד 4 · schema.ts עם 3,000 שורות של Zod ידני

קבצים

  • lib/db/schema.ts — ~20 טבלאות × 3 סכמות ידניות (insert/select/type)
  • 36 קבצי migration ידניים + snapshots

הבעיה

כל טבלת Drizzle מלווה בשלוש הגדרות Zod ידניות (insert, select, type) שמשכפלות את השמות והסוגים. הוספת עמודה = עריכת 4 מקומות (טבלה + 3 סכמות). התוצאה: שורות רבות של קוד שטחי שמספק מעט מידע — בדיוק ההגדרה של מודול רדוד (ממשק מורכב כמו מימוש).

הפתרון

שימוש ב-drizzle-zod (או גנרטור דומה) להפקת הסכמות מהטבלאות, עם שכבת refinement אחת למשמעויות עסקיות (enums, constraints). ספקנות: פורמט הקוד הנוכחי נצרך על ידי הקומפוננטות, והמגירה גדולה — נדרשת בדיקת כיסוי טובה לפני.

יתרונות

  • Leverage: שינוי סכמה = מקור אמת אחד → schema מופק.
  • Deletion test: מחיקת 2/3 מהשורות מרכזת מורכבות, לא מזיזה.
  • מקטין את אחד הקבצים הגדולים בפרויקט בכ-60%.

🏆 ההמלצה המובילה

להתחיל במועמד 2 — איחוד אדפטר הסוכנים. הוא הקונקרטי ביותר: מחיקה אמיתית של שכפול ידע, סיכון נמוך (התנהגות אחידה במקום שני מקורות אמת), והוא מחזיק את הליבה של מה שהפלטפורמה עושה — להריץ סוכנים. מיד אחריו, מועמד 1 יפתור את סתירת ה-routePrompt שעלולה להוביל לבחירת מודלים שגויה (model names מיושנים ב-smart-router מול חדשים ב-router).

ערב רבה: בפרויקט אין CONTEXT.md (גלוסר דומיין) ואין ADRs. לאורך הסריקה הבחנתי ששפות הדוגמנות של "משימה", "עובד", "תור" משתנות בין המודולים — מסמך דומיין יחיד ישפר את הניווט של כל סוכן עתידי.
